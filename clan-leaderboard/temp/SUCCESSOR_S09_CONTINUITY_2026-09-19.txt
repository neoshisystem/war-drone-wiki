3. Manual Identity Fingerprinting
============================================================
STATUS: INTENTIONAL DESIGN

There is no automatic identity-fingerprint engine in the repository.

Historical workflow:
1. Inspect leaderboard screenshots and profile screenshots manually.
2. Match stable identity using technical/visual evidence such as Stage, 25mm, Hydra, Hellfire, Kills, Clan Medals, honors and other visible attributes.
3. Use the canonical player_id in the incoming JSON when the identity is already known.
4. For a genuinely new identity, explicitly mark confirmed_new_identity=true.
5. If identity is ambiguous, do not guess.

The repository stores the final identity mapping, not a formal reasoning/audit record of every manual fingerprint comparison.

There is currently no canonical per-match audit schema for "why this screenshot was matched to this player_id".

This is not evidence that screenshots were unimportant; it means the evidence review happened outside canonical JSON and only the final identity mapping was persisted.

6. confirmed_new_identity=true
============================================================
STATUS: CONFIRMED INVARIANT

The field is for a genuinely new identity when the tool cannot resolve the player to an existing registry identity.

Valid new-identity pattern:
{
  "display_name": "...",
  "confirmed_new_identity": true,
  ...
}

player_id is intentionally omitted for a new identity; the tool allocates the next sequential ID.

If an explicit player_id is supplied:
- it must already exist in players.json;
- unknown explicit player_id causes ingestion failure.

Do not use confirmed_new_identity=true as a substitute for an unresolved existing identity.

The implementation is permissive enough that a known existing player with confirmed_new_identity=true is not treated as a new player because the existing player resolves first. Nevertheless, semantically, the flag should only be used for genuinely new identities.

8. Returning players and membership gap
============================================================
STATUS: CONFIRMED INVARIANT

Period and Lifetime/Cumulative have deliberately different semantics.

Period Delta:
- compares only to the immediately previous snapshot for the current identity when that identity was observed there;
- after a membership gap, the returning player has no immediately previous observation;
- therefore period contribution returns to baseline.

Lifetime/Cumulative:
- preserves stable identity history across gaps;
- uses the last historical observation available to cumulative state;
- when the identity returns, cumulative earned values continue from its prior cumulative history.

This is tested explicitly in tools/test-performance.js:
- the synthetic gap player has period Clan/Kill = 0 and baseline=true after return;
- cumulative Clan/Kill continue from the earlier cumulative state and add the new post-return activity.

Canonical invariant:
RETURNING PLAYER => PERIOD BASELINE, LIFETIME HISTORY PRESERVED.

============================================================
9. Removed players
============================================================
STATUS: CONFIRMED INVARIANT

A removed player:
- has no current observation;
- contributes zero to the current Period Delta;
- remains in historical identity/cumulative state.

When that same player returns:
- period calculation is based on the immediate previous snapshot only; if there is a gap, the returned player is baseline for the current period;
- cumulative calculation continues from the historical cumulative observation.

Example family:
PERSIA-P-0049 existed in S06, was absent in S07, and returned later. This identity is not deleted or reallocated.

Memberships are interval-based and a later return creates a new active interval rather than erasing history.

21. Membership model
============================================================
STATUS: CONFIRMED INVARIANT

Membership is interval-based:
- from_snapshot
- through_snapshot
- status
- optional start_event/end_event/end_precision

When a player leaves and later returns:
- a new membership interval is created;
- historical ended interval is preserved.

through_snapshot is the last snapshot in which that membership interval is observed.

Current ingestion behavior:
- existing active membership is extended to the new snapshot when the player is still present;
- added identities get a new active interval;
- removed identities have their active interval closed at the previous snapshot.
